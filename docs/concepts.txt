CONCEPT 1: DATABASE MIDDLEWARE
--------------------------------------------------------------------------------
1. Plain English:
   Middleware is code that sits directly between your application logic and the
   database. Instead of your app talking directly to PostgreSQL, every query must
   first pass through the middleware.

2. Physical Flow Underneath:
   [Application Code]
           │
           │ 1. calls vault.execute("SELECT * FROM customers")
           ▼
   [VaultDB Middleware]
           │ 2. Inspects caller: who is asking? (e.g. user='sarah', role='writer')
           │ 3. Inspects SQL: does role have permission for this table & action?
           │ 4. Checks for sensitive columns (password, ssn, credit_card)
           │ 5. Dispatches query to PostgreSQL over network socket
           │ 6. Writes audit record: (timestamp, user, query, rows, status)
           ▼
   [PostgreSQL Database]
           │ 7. Returns rows to Middleware
           ▼
   [Application Code receives result rows]

3. Code Structure:
   def execute(query, params, app_user, user_role):
       # 1. Authorize
       if not is_allowed(user_role, query):
           log_violation(app_user, user_role, query)
           raise PermissionError("Access Denied")

       # 2. Check sensitivity
       is_sensitive = check_sensitive(query)

       # 3. Execute
       with conn.cursor() as cur:
           cur.execute(query, params)
           results = cur.fetchall()
           row_count = cur.rowcount

       # 4. Audit Log
       write_audit_log(app_user, user_role, query, row_count, is_sensitive)

       return results

CONCEPT 2: HOW PYTHON TALKS TO POSTGRESQL (TCP/IP SOCKETS & PSYCOPG)
--------------------------------------------------------------------------------
1. Plain English:
   PostgreSQL is an independent server program running on your machine.
   Python is an independent program running on your machine.
   They do NOT share memory. They talk to each other over an internal network
   connection called a TCP/IP socket (usually on port 5432).

2. Physical Flow Underneath:
   - Python code calls `cursor.execute("SELECT * FROM customers")`.
   - `psycopg` formats that text into binary packets following the PostgreSQL
     Frontend/Backend Protocol.
   - Operating system sends the bytes through the TCP/IP socket (127.0.0.1:5432).
   - PostgreSQL engine receives the bytes, parses the SQL, fetches data from disk
     or RAM cache, and sends result rows back as binary packets.
   - `psycopg` decodes those binary packets into Python tuples/dictionaries.

3. Why Direct psycopg Instead of an ORM?
   - Zero hidden queries or magic.
   - We see the exact SQL text the user wrote.
   - Extremely fast and easy to explain in an exam.

CONCEPT 3: IMMUTABILITY AT THE DATABASE ENGINE LEVEL
--------------------------------------------------------------------------------
1. Plain English:
   "Immutable" means once a record is inserted, it can NEVER be updated or deleted.
   If someone tries to run `UPDATE audit_logs` or `DELETE FROM audit_logs`, the
   database engine itself rejects it and throws an error.

2. How PostgreSQL Enforces It:
   We use TWO defense layers:

   Layer A: PostgreSQL Permissions (GRANT / REVOKE)
   - Grant the app user permission to INSERT and SELECT.
   - Explicitly REVOKE permission to UPDATE, DELETE, or TRUNCATE:
     REVOKE UPDATE, DELETE, TRUNCATE ON vault_audit.audit_logs FROM vault_app;

   Layer B: PostgreSQL Engine Trigger
   - Even if a query bypasses the permission check, a BEFORE UPDATE OR DELETE trigger
     intercepts the row modification and immediately raises an exception.

3. Trigger Code:
   CREATE OR REPLACE FUNCTION vault_audit.prevent_log_tampering()
   RETURNS TRIGGER AS $$
   BEGIN
       RAISE EXCEPTION 'Audit records are immutable and cannot be updated or deleted.';
   END;
   $$ LANGUAGE plpgsql;

   CREATE TRIGGER trg_audit_immutable
   BEFORE UPDATE OR DELETE ON vault_audit.audit_logs
   FOR EACH ROW EXECUTE FUNCTION vault_audit.prevent_log_tampering();

CONCEPT 4: APPLICATION IDENTITY VS. DATABASE IDENTITY
--------------------------------------------------------------------------------
1. Plain English:
   - Database Identity: The single user account Python uses to log in to PostgreSQL
     (e.g., `vault_app_user`).
   - Application Identity: The actual human or employee using the application
     (e.g., `sarah@company.com` or `john@company.com`).

2. Why This Matters:
   PostgreSQL native logs only see `vault_app_user` for all queries because all
   requests share the same database connection pool.
   PostgreSQL has no idea who "Sarah" or "John" is.
   VaultDB bridges this gap by receiving the human user's name in Python and
   storing it in the audit table alongside the query.


--------------------------------------------------------------------------------
CONCEPT 5: DUAL SCHEMA DESIGN (app_data vs vault_audit)
--------------------------------------------------------------------------------
1. Plain English:
   A schema in PostgreSQL is like a folder inside a database.
   Instead of putting all tables in the default `public` schema, we separate them:
   - `app_data`: Holds business tables (customers, orders, reports).
   - `vault_audit`: Holds audit tables and immutability triggers.

2. Why:
   - Clean separation of business logic from security records.
   - Allows different permission rules: normal users can edit `app_data.customers`,
     but nobody can edit `vault_audit.audit_logs`.


--------------------------------------------------------------------------------
CONCEPT 6: PYTHON VIRTUAL ENVIRONMENTS (venv)
--------------------------------------------------------------------------------
1. Plain English:
   `venv` is an isolated sandbox folder inside your project.
   Instead of installing libraries globally into your Windows system directory,
   Python installs packages (like `psycopg`) directly into `venv/`.

2. Why:
   - Prevents version conflicts with other Python projects.
   - Makes the project easily reproducible for teammates and professors via
     `requirements.txt`.

CONCEPT 7: SQL DATA DEFINITION & CONSTRAINTS (schema.sql)
--------------------------------------------------------------------------------
1. Plain English:
   DDL (Data Definition Language) defines the rules, types, and relationships
   governing how data is stored on disk.

2. What Each Column Type & Constraint Does:
   - `SERIAL / BIGSERIAL`: An auto-incrementing integer managed by a PostgreSQL
     sequence. `BIGSERIAL` handles trillions of rows (ideal for high-volume audit logs).
   - `PRIMARY KEY`: Guarantees every row has a unique, non-null identifier.
   - `FOREIGN KEY (... REFERENCES ...)`: Enforces relational integrity. You cannot
     create an order for a customer_id that does not exist.
   - `TIMESTAMP WITH TIME ZONE`: Stores timestamps in UTC with timezone offset,
     preventing ambiguity across international audit reviews.
   - `TEXT`: Unbounded variable-length character string, allowing full SQL query
     statements of any length to be audited without truncation.
   - `ON CONFLICT DO NOTHING`: Makes seed data insertion idempotent (safe to run
     multiple times without throwing duplicate key errors).


--------------------------------------------------------------------------------
CONCEPT 8: IDEMPOTENCE (What it means and why it matters)
--------------------------------------------------------------------------------
1. Plain English:
   An operation is "idempotent" if doing it ONCE has the exact same result as
   doing it 100 TIMES in a row.

2. Real-World Analogy:
   - NOT Idempotent: Pressing a "Volume UP" button.
     * Press it 1 time  --> Volume goes to 11.
     * Press it 5 times --> Volume goes to 15. (The result keeps changing).

   - IDEMPOTENT: Pressing an Elevator "Floor 5" button.
     * Press it 1 time  --> The elevator goes to Floor 5.
     * Press it 10 times --> The elevator still just goes to Floor 5.
     * No error occurs, and the end state is identical.

3. In Databases & VaultDB:
   - Non-idempotent script:
     `INSERT INTO customers (email) VALUES ('alice@example.com');`
     Run it twice --> Crashes with "duplicate key error" on the 2nd run.

   - Idempotent script:
     `INSERT INTO customers (email) VALUES ('alice@example.com') ON CONFLICT (email) DO NOTHING;`
     Run it 1 time or 50 times --> Alice exists once, and the script succeeds every time.

CONCEPT 9: QUERY PARSING & SENSITIVE DETECTION (Regex & Word Boundaries)
--------------------------------------------------------------------------------
1. Plain English:
   To log a query intelligently, VaultDB inspects the SQL string to extract:
   - The Action: `SELECT`, `INSERT`, `UPDATE`, `DELETE`
   - The Target Table: `customers`, `orders`
   - Sensitive Keywords: `ssn`, `credit_card`, `password`

2. Why `\b` (Word Boundary) in Regex?
   If someone searches for a column named `assignment`, we do NOT want our detector
   to flag it just because the letters `ssn` appear inside the word `a-ssn-ignment`.
   Using `\bssn\b` ensures we only match the exact word "ssn".


--------------------------------------------------------------------------------
CONCEPT 10: PARAMETERIZED QUERIES (Preventing SQL Injection)
--------------------------------------------------------------------------------
1. Plain English:
   When writing data into PostgreSQL, never stitch user strings directly into
   SQL with f-strings (e.g., `f"INSERT INTO logs VALUES ('{user}')"`).
   An attacker could send `user = "admin'); DROP TABLE customers; --"`.

2. The Safe Approach in VaultDB:
   We pass SQL templates with `%s` placeholders and send values separately:
   `cur.execute("INSERT INTO logs (user) VALUES (%s)", (user,))`
   The `psycopg` driver sends the query text and the data parameters to PostgreSQL
   separately over the wire, making SQL injection physically impossible.


--------------------------------------------------------------------------------
CONCEPT 11: PYTHON CONTEXT MANAGERS (`with conn.cursor() as cur:`)
--------------------------------------------------------------------------------
1. Plain English:
   In database programming, a "cursor" is a handle to execute queries and fetch
   results. If you open cursors without closing them, PostgreSQL runs out of memory
   (Connection Leak).

2. Why `with` statement?
   The `with` statement is a Context Manager. It guarantees that the cursor is
   immediately closed and cleaned up as soon as the indented block finishes,
   even if a Python exception or error occurs inside.


--------------------------------------------------------------------------------
CONCEPT 12: `try / except / finally` IN AUDIT LOGGING
--------------------------------------------------------------------------------
1. Plain English:
   In security logging, the most critical queries to log are often the FAILED ones
   (e.g., an attacker trying to access unauthorized tables or running bad syntax).

2. How VaultDB Handles It:
   - `try`: Attempt the SQL query.
   - `except`: If PostgreSQL throws an error, catch it and mark `status = 'ERROR'`.
   - `finally`: Regardless of success or failure, the `finally` block ALWAYS executes
     and inserts the audit entry into `vault_audit.audit_logs`.


--------------------------------------------------------------------------------
CONCEPT 13: `cur.description` VS `cur.rowcount`
--------------------------------------------------------------------------------
1. Plain English:
   How does Python know if a query was a `SELECT` (which returns data rows) or an
   `INSERT/UPDATE/DELETE` (which modifies rows)?

2. How psycopg Handles It:
   - If `cur.description is not None`: The query returned rows (`SELECT`).
     We call `cur.fetchall()` and count the returned records (`len(results)`).
   - If `cur.description is None`: It was a data modification query.
     `cur.rowcount` tells us how many rows were inserted, updated, or deleted.


--------------------------------------------------------------------------------
CONCEPT 14: HONEST MIDDLEWARE OVERHEAD & BENCHMARKING
--------------------------------------------------------------------------------
1. Plain English:
   Every middleware that intercepts and audits queries adds a tiny amount of latency.
   Why? Because for every business query executed, the middleware must:
   - Parse the SQL string in Python (~0.01 ms).
   - Send a secondary `INSERT INTO vault_audit.audit_logs` to PostgreSQL (~1.0 ms).

2. Honest Benchmark Results:
   - Raw psycopg query time: ~0.38 ms
   - VaultClient query time: ~1.50 ms
   - Overhead per query:     ~1.11 ms

3. Why this matters:
   The overhead is simply the physical time needed to write the audit record into
   PostgreSQL. No fake claims are made—the audit trail is synchronous and guaranteed.

MASTER VIVA QUESTIONS & ANSWERS (ORAL EXAM PREPARATION)
================================================================================

Q1: What is VaultDB?
A1: VaultDB is an audit logging and access control database middleware for
    PostgreSQL designed to meet compliance requirements like GDPR and HIPAA.

Q2: Is VaultDB a database?
A2: No. It is a middleware layer sitting between client applications and PostgreSQL.
    PostgreSQL is the underlying database engine.

Q3: Why build middleware if PostgreSQL already has native logging?
A3: PostgreSQL logs write to server text files with the shared database role
    (e.g., 'app_user'). PostgreSQL cannot identify the human application user
    (e.g., Sarah vs John), nor does it provide structured queryable audit tables.

Q4: How does Python communicate with PostgreSQL?
A4: Python opens a TCP/IP socket connection to port 5432 and uses the psycopg
    driver to format SQL commands into PostgreSQL's native wire protocol.

Q5: Why did you use regex instead of an AST parser library for SQL?
A5: For V1, regex pattern matching is extremely fast (microseconds), introduces
    zero external dependencies, and accurately extracts standard CRUD actions
    and target tables without bloating the codebase.

Q6: Why use word boundaries `\b` when detecting sensitive keywords like `ssn`?
A6: To prevent false positives. Without `\b`, a harmless word like 'assignment'
    would trigger a sensitive alert because 'ssn' is inside it.

Q7: How do you prevent SQL injection when writing audit records?
A7: By using parameterized queries with `%s` placeholders. The psycopg driver
    transmits the query structure and parameter values separately to PostgreSQL.

Q8: Why is `finally` used in the query execution method?
A8: To guarantee that audit records are written 100% of the time, even if the
    user's query throws a syntax error or runtime database exception.

Q9: What causes the ~1.1ms overhead in VaultClient?
A9: The overhead comes from executing the secondary synchronous INSERT query to
    persist the audit record into vault_audit.audit_logs in PostgreSQL.

Q10: What makes the audit log immutable?
A10: PostgreSQL permissions (REVOKE UPDATE, DELETE, TRUNCATE) and a PostgreSQL
     BEFORE UPDATE OR DELETE trigger that aborts any row alteration attempt.

Q11: Can a PostgreSQL superuser modify the audit log?
A11: Yes. A superuser has administrative authority over the engine itself. VaultDB
     protects against all application users and normal database roles.
